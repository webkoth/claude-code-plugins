# Developer Thinking Rubric — 7 Signals

Этот документ — таксономия сигналов мышления разработчика, наблюдаемых в логе AI-assisted interview сессии. Используется LLM-анализатором для генерации отчёта по кандидату.

**Принципы оценки:**

1. **Один пример — не сигнал.** Категория получает score только если паттерн повторился ≥2 раз (или один раз очень ярко).
2. **Контекст важнее ярлыка.** "Не запустил тесты" не red flag если задача без тестов; "много вопросов AI" не red flag если задача под Greenfield.
3. **Не путать скорость с качеством мышления.** Медленный кандидат может мыслить лучше быстрого. Time-to-completion — отдельная метрика, не входит в 7 сигналов.
4. **Red flag доминирует.** Если в категории сильный red flag (paradigm violation), он перекрывает любые green-сигналы в этой же категории.
5. **N/A валидно.** Если данных в логе мало для оценки — выставляем `null` и пишем "недостаточно сигналов", не выдумываем.

---

## Scoring

Каждая категория получает score `0..5`:

| Score | Meaning |
|-------|---------|
| 5 | Strong evidence of mastery, multiple green signals |
| 4 | Solid, occasional minor lapse |
| 3 | Mixed — green и red примерно равны |
| 2 | Mostly red, occasional green |
| 1 | Strong red flags dominate |
| 0 | Critical anti-pattern (e.g. отказался от верификации после прямого указания) |
| null | Недостаточно сигналов в логе |

**Overall % fit** = `Σ (score × weight) / Σ (weight × 5) × 100`, считая только категории с не-null score. Если красная категория критическая для роли (запись в `critical` блоке `profile.yaml`) и score ≤ `threshold` — overall ограничен по `cap_overall_pct`. Дефолтный cap при отсутствии явного profile — 40%. Все веса и custom flags видны кандидату через `profile.yaml`.

## 1. Promptcraft — Качество промптов

Насколько точно, контекстно и декомпозированно кандидат формулирует задачи AI.

**Observable behaviors:**
- Указание стека, ограничений, ожидаемого формата ответа
- Декомпозиция большой задачи на конкретные шаги
- Itertive refinement (пересмотр промпта после неудачного ответа)
- Указание границ (что НЕ делать)
- Использование примеров входа/выхода

**Green signals:**
- "Прежде чем писать код, предложи 2-3 подхода и их trade-offs"
- "Только diff для файла X, не переписывай целиком. Должно работать на Node 18, без новых dependencies"
- Reformulation после неудачного ответа: "вот что я имел в виду..." с уточнением
- Указание ограничений: "не использовать regex, парсить через AST"

**Red signals:**
- One-liner без контекста: "сделай рассылку", "почини баг", "напиши код"
- Повтор того же промпта дословно когда не сработал в первый раз
- Огромный wall-of-text без структуры
- "Сделай как лучше" без указания критерия "лучше"

**Anchor phrases для детекции:**
- Green: "trade-off", "ограничение", "только/без", "сначала", "формат ответа"
- Red: повторы промптов, отсутствие контекста стека/файла

## 2. Critical Reception — Критическое восприятие AI-ответов

Принимает ли кандидат код/советы AI вслепую или верифицирует, оспаривает, упрощает. Способность распознать AI sycophancy (когда модель подстраивается под неверную гипотезу пользователя).

**Observable behaviors:**
- Запуск AI-кода без чтения vs предварительная проверка глазами
- Reject AI-предложений с обоснованием
- Вопросы "почему X, а не Y?"
- Распознавание hallucination (несуществующие API, методы, библиотеки)
- Замечание противоречий в ответах AI

**Green signals:**
- "Подожди, ты добавил библиотеку X — она нам не нужна, можно через стандартный модуль"
- "Объясни почему именно этот подход, а не более простой?"
- Останавливает tool call AI до выполнения после прочтения diff
- Замечает что AI предлагает несуществующий метод/опцию
- "Это решение работает, но я хочу понять почему"

**Red signals:**
- Принимает каждый ответ AI без обсуждения, сразу запускает
- Повтор того же запроса когда AI выдаёт ту же ошибку
- Не замечает противоречия между ответами AI в одной сессии
- Импортирует библиотеку которую AI предложил, не проверив существует ли
- Соглашается с AI после возражения AI ("ой да, ты прав") без проверки

**Anchor phrases:**
- Green: "почему", "стоп", "подожди", "это лишнее", "проще", "не нужен"
- Red: blindly accepting tool call results, отсутствие push-back

## 3. Verification & Testing — Верификация и тестирование

Проверяет ли кандидат предположения через тесты, минимальные репро-сценарии, output программ.

**Observable behaviors:**
- Запуск тестов после изменения
- Написание нового теста/test case перед фиксом
- Создание minimal reproducible example
- Чтение output программы построчно
- Использование REPL/scratch файлов для проверки гипотез
- Smoke-test перед "готово"

**Green signals:**
- Запускает `npm test` / `pytest` / `cargo test` после каждого значимого edit
- "Прежде чем менять X, давай напишем failing test"
- Пишет одноразовый скрипт для проверки assumption ("работает ли parseInt с этим форматом")
- Читает actual vs expected в test output вместо "оно сломалось"
- Создаёт небольшой sample input чтобы проверить функцию изолированно

**Red signals:**
- Edits → "должно работать" без запуска
- Игнорирование test output ("ну там ошибка, давай дальше")
- "А что если так?" без проверки → "не сработало, давай ещё что-то"
- Не пишет новых тестов когда задача про багфикс
- Принимает за работающее решение которое падает на edge case

**Anti-pattern:** "Hypnotising the error" (по Мокевнину) — copy/paste ошибки в AI без новой информации, без локализации.

## 4. Debugging Methodology — Методология дебага

Системный bisection vs random guessing. Сколько времени тратится на одну "стену" до смены подхода.

**Observable behaviors:**
- Минимальный воспроизводимый кейс
- Логирование/print для локализации точки расхождения
- Чтение stack traces построчно
- Возврат изменений когда подход не работает
- Bisection (git bisect, бинарный поиск виновной строки)
- Гипотеза → проверка → вывод (loop)

**Green signals:**
- "Давай добавим лог здесь и здесь, чтобы понять где значение теряется"
- Цитирует конкретную строку error и идёт по trace
- Откатывает изменение которое не помогло, прежде чем пробовать следующее
- Изолирует подозрительную функцию в одиночный скрипт
- "Гипотеза: проблема в Х. Проверка: запустим Y. Результат: гипотеза неверна. Новая гипотеза: ..."

**Red signals:**
- "Попробуй другой подход" 4-й раз подряд, AI меняет одну строку каждый раз
- Копирование того же error message без изменения промпта
- Каскад правок поверх друг друга, ни одна не откачивается
- "Hypnotising": тыкается в одно место 20+ минут вместо смены угла
- Угадывание ("может, импорты в другом порядке?") без проверки

**Anchor:** длительность "залипа" — если кандидат >15 мин крутится на одной ошибке без новой информации в логе — strong red signal.

## 5. Architecture Steering — Архитектурное направление AI

По Мокевнину: AI подстраивается под пользователя. Если у кандидата неверная модель архитектуры, AI генерирует ошибочный или избыточный код. Кандидат либо корректирует вектор, либо усиливает галлюцинацию.

**Observable behaviors:**
- Объяснение AI существующей архитектуры проекта перед изменениями
- Refusing overengineering (Repository + Factory + Service + DTO для одного эндпоинта)
- Понимание trade-offs предложенных AI решений
- Упрощение AI-решений когда они избыточны
- Корректировка AI когда тот идёт в неверном направлении

**Green signals:**
- "Это слишком сложно для нашего масштаба, давай решим через middleware"
- "У нас уже есть X в utils/, переиспользуй его"
- "Не используй Redux — приложение на 3 экрана, useState достаточно"
- Объясняет домен задачи и существующие соглашения проекта
- "AI предложил поменять архитектуру — отклоняю, у нас фиксированная"

**Red signals:**
- Соглашается на любую сложность которую AI предложил
- Не замечает что AI ввёл новые dependencies/abstractions
- Дублирует существующую логику потому что AI её не нашёл, а кандидат не указал
- Позволяет AI вести себя в архитектурный тупик (например, mixing concerns между layers)
- "Давай добавим Kafka" в проекте на 100 RPS

**Critical anti-pattern:** "Galloping galaxy-brain" — кандидат активно поощряет AI к усложнению ("а ещё добавь...", "сделай через X pattern").

## 6. Environment & Tooling — Самостоятельность в окружении

По Мокевнину — 70% кандидатов отсеиваются ещё до кода: не могут поставить версии Ruby, разобраться с Bash, прочитать docs. Это базовый layer; без него высокие сигналы в других категориях недостоверны.

**Observable behaviors:**
- Настройка окружения (deps install, env vars, version managers)
- Использование git правильно (status, diff, log, branch, stash)
- Чтение docs / source кода когда нужно
- Знание базовых CLI tools (find/grep/jq/curl)
- Восстановление после ошибок setup

**Green signals:**
- `git status` / `git diff` перед commit
- `rg "fn handler"` или аналог для поиска
- Чтение `package.json` / `pyproject.toml` чтобы понять scripts
- `cat .env.example` перед запуском
- Прочитал README перед "как это запускается?"

**Red signals:**
- "Файл не найден" → продолжает тыкаться вместо `ls`/`find`
- Не может разрешить конфликт версий node/python
- `git push` без `git status`/`git diff`
- "Эта команда не работает" — на самом деле не установлен tool
- Не использует terminal, ждёт пока AI всё сделает за него

**Note:** Эта категория — base layer. Если score ≤ 1 — overall % fit не превышает 50% независимо от других.

## 7. Metacognition — Метакогниция

Озвучивание собственных гипотез; распознавание тупика; знание своих границ.

**Observable behaviors:**
- Формулирование гипотез вслух ("я думаю проблема в X")
- Признание неуверенности ("я не уверен в этом подходе")
- Смена подхода при тупике
- Уточняющие вопросы по требованиям задачи перед началом
- Reflective pauses ("стоп, давай разберёмся где я")

**Green signals:**
- "Я не знаю эту библиотеку, давай сначала прочитаю README"
- "Третий раз пытаюсь через Z — попробую другой подход"
- Уточняет неясности задачи перед codingом
- "Не уверен что эта функция async — проверим"
- Self-corrects при озвучивании: "о, я подумал и понял что неверно..."

**Red signals:**
- Продолжает тот же подход после 3+ предупреждений AI
- "Должно работать" без основания
- Никаких вопросов по неясной задаче — сразу пишет код
- Не признаёт ошибку даже когда выход явный
- "Я знаю это" — потом промахивается на базовом

## Additional signals to surface (out of v1 scoring, упоминаются в отчёте если наблюдались)

Эти сигналы не входят в 7 scored категорий v1, но LLM-анализатор должен их подсветить если они проявились — они дают цвет HR-у на собеседовании и являются предсказывающими senior-level работу с AI:

- **Decomposition & Planning (Декомпозиция).** Зелёный: короткий пронумерованный план перед правками. Красный: ныряет в код без плана и теряется в середине.
- **Context Hygiene (Гигиена контекста).** Зелёный: ссылается на конкретные файлы/символы, не паcтит всю кодобазу в AI; суммирует длинные threads. Красный: paste-everything, не вычищает.
- **Risk & Reversibility (Риск и обратимость).** Зелёный: `git commit` перед destructive ops, спрашивает AI "что может сломаться?", использует dry-run. Красный: `rm -rf` без подтверждения, принимает destructive AI suggestions без чтения.
- **Communication & Justification (Объяснение решений).** Зелёный: каждое решение сопровождается обоснованием, осмысленные commit messages. Красный: silent acceptance, commit message = "fix".
- **Knowledge Boundaries (Границы знания).** Зелёный: "не помню точную сигнатуру — проверю docs". Красный: уверенно повторяет AI hallucination как факт, никогда не говорит "не знаю".

## Cross-cutting anti-patterns (выносятся в отдельный блок отчёта)

Эти паттерны не привязаны к одной категории, но если зафиксированы — упоминаются явно в отчёте:

1. **Hypnotising the error** (Мокевнин) — 15+ минут на одной ошибке без новой гипотезы.
2. **Galloping galaxy-brain** — кандидат активно усложняет вместе с AI.
3. **AI-only operator** — кандидат вообще не пишет код руками и не читает diff (всё делегирует, не верифицирует).
4. **Sycophancy unawareness** — AI явно поменял позицию под кандидата (LLM согласился с неверным утверждением), кандидат не заметил.
5. **Silent confusion** — на сложном этапе кандидат молча копирует AI ответы без переформулирования промпта.

## Reporting format

Отчёт LLM-анализатора должен включать:

- **Per-category scores** (0..5 или null) с обоснованием в 2-3 предложения и 2-3 цитатами из лога
- **Cross-cutting anti-patterns** если встретились
- **Weighted scoring** таблица + **Overall % fit** (применяя `profile.yaml` сессии — веса и custom flags видны кандидату)
- **Custom flag matches** — какие custom green/red flags из profile сработали
- **Critical caps applied** — какие критические категории зафиксировали потолок
- **Top 3 green signals** — лучшие моменты сессии
- **Top 3 red signals** — слабые места
- **Recommendation** tier — STRONG HIRE / HIRE / NEEDS DEEPER INTERVIEW / NO HIRE
- **What to probe in live follow-up** — что HR / team lead стоит дополнительно проверить
- **Notes for the candidate** — конструктивная обратная связь, кандидат уходит со звонка с пониманием куда расти

Каждый сигнал в отчёте ссылается на конкретный timestamp/строку лога — чтобы кандидат, HR и team lead при аудите могли вернуться к источнику.
